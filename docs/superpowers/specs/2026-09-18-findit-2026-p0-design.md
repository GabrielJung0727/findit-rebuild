# FindIt 2026 — P0 (코어 배틀) 설계 명세

- **작성일**: 2026-09-18
- **근거 문서**: `FindIt 게임 분석 및 2026버전 개발 기획서.pdf` (Part 1 원작 명세 / Part 2 2026 로드맵)
- **상태**: 승인됨 — 구현 계획(writing-plans) 대상
- **범위**: P0 수직 슬라이스만. P1~P5는 §11 로드맵에 경계만 정의한다.

---

## 1. 목표와 비목표

### 목표

원작 *FindIt: The Battle* (2012–2013, Android/Java)의 대전 재미를 보존한 채, 2026년 기준
기술 스택으로 **끝까지 동작하는 좁은 한 줄기**를 만든다. 로그인부터 결과 정산까지 한 사람이
실제로 플레이할 수 있어야 하며, 그 과정의 모든 판정은 서버가 내린다.

### 비목표 (P0에서 의도적으로 제외)

상점 · 인벤토리 UI · 스킬트리 전체 · 랭킹 · 공지 · 친구 초대 · 배틀패스 · 가챠 · 리워드 광고 ·
2v2 · 길드 레이드 · AI 생성 콘텐츠 · UGC · WebGL/Steam/Smart TV 빌드 · IAP.

이들은 P0가 선 뒤 각자 스펙 사이클을 갖는다. P0 설계는 이들이 **꽂힐 자리만** 비워둔다.

## 3. 게임 규칙 (확정 수치)

### 3.1 기본 규칙

| 항목 | 값 | 출처 |
|---|---|---|
| 제한시간 | **40초** | PDF (초기안 99초에서 개정) |
| 이미지당 정의된 틀린 부위 | **7개** | PDF + 원작 `Objects.java` |
| 실제 노출 개수 | **5개** (7개 중 랜덤) | PDF + 원작 `GameView.java:2657` (`5 - mLeftNum`) |
| 승리 조건 | 5개 선취, 또는 40초 만료 시 더 많이 찾은 쪽 | PDF |
| 무승부 | 각자 본인이 찾은 코인만 획득 | PDF |
| 카운트다운 | 양쪽 준비 완료 후 3초 | PDF |
| 보상 | 부위 1개당 경험치 100 + 코인 1. 승자가 상대 코인 독식 | PDF |
| 오답 터치 | 입력 잠금 2,000ms + 콤보 리셋 + 햅틱 | 원작 `GameView.java:3931` (`mDimTime = 20`) |

> **개정 기록**: 기존 `docs/wiki/Game-Design.md`는 "7개 전부 찾으면 승리"로 기술한다.
> PDF가 상위 문서이고 원작 코드와도 일치하므로 **5-of-7을 채택**한다. 위키는 P0 완료 후 갱신한다.

### 3.2 점수 · 콤보

```
승자 점수 = findNum × 50 + 100 + comboBonus
패자 점수 = findNum × 50 + comboBonus
```

| 콤보 | 점수 보너스 | 시간 보너스 |
|---:|---:|---:|
| 1 | +100 | +1초 |
| 2 | +200 | +2초 |
| 3 | +400 | +4초 |
| 4 이상 | +700 | +7초 |

콤보 리셋: 본인 오답 터치 / 상대가 정답 발견 / 게임 종료.

### 3.3 스킬 방해 시간 공식 (PDF 명시)

```
최종 화면 가림 시간
  = 스킬 기본 시간
  + 공격자 공격력
  + 공격자 아이템 추가시간
  − 방어자 방어력
  − 방어자 아이템 감쇄시간
```

하한은 **0초**로 clamp한다 (음수 가림 시간은 정의되지 않음 — 본 스펙에서 명시적으로 정함).

### 3.4 기본 스킬 트리

PDF Part 1 §3 표를 그대로 채택한다. 총 29 스킬.

| 계열 | 단계 | 지속시간 | 언락 레벨 | 필요 포인트 | 선행 요건 |
|---|---:|---|---|---:|---|
| 손도장 | 1–9 | 1.0 → 1.8초 (+0.1/단계) | Lv 1–17 (홀수) | 1 | 직전 손도장 |
| 발도장 | 1–5 | 1.9 → 2.3초 (+0.1/단계) | Lv 10–18 (짝수) | 2 | 손도장 5 |
| 그림자 | 1–5 | 2.0 → 2.4초 (+0.1/단계) | Lv 20–28 (짝수) | 3 | 손도장 8, 발도장 5 |
| 분신 | 1–5 | 2.5 → 2.9초 (+0.1/단계) | Lv 30–42 (+3Lv) | 4 | 그림자 5 |
| 유령 | 1–5 | 3.0 → 4.0초 | Lv 45–57 (+3Lv) | 5 | 분신 5, 발도장 5, 손도장 10 |

레벨업마다 스킬 포인트 1점 획득. 선행 요건 충족 시에만 상위 습득.

> **알려진 밸런스 이상 (수정하지 않고 보존)**: 그림자1(2.0초)은 이미 보유한 발도장5(2.3초)보다
> 짧은데 포인트 비용은 3점으로 더 비싸다. PDF 수치를 임의로 고치지 않고 그대로 구현하되,
> P1 밸런싱 단계의 검토 항목으로 남긴다.
>
> **선행 요건 모순**: 유령 계열은 "손도장 10"을 요구하지만 손도장은 9단계까지만 존재한다.
> **손도장 9로 해석**하여 구현한다.

### 3.5 스킬 비주얼 매핑 (본 스펙에서 결정)

PDF는 기본 스킬 트리(§3.4)와 "아이템 스킬 및 화면 방해 효과" 표를 별도로 제시하나,
레거시 에셋에는 후자 8종의 이펙트만 존재한다. 메커니즘은 §3.4를, 비주얼은 아래 매핑을 따른다.

| 스킬 계열 | 이펙트 에셋 | 아이콘 에셋 | 원 명칭 |
|---|---|---|---|
| 손도장 | `efct_skill_01` | `game_skill_01` | 고양이 발톱 |
| 발도장 | `efct_skill_02` | `game_skill_02` | 강아지 발자국 |
| 그림자 | `efct_skill_101` | `game_skill_101` | 폭발 |
| 분신 | `efct_skill_102` | `game_skill_102` | 불꽃 |
| 유령 | `efct_skill_103` | `game_skill_103` | 눈꽃 |
| 베리 아이템 (강력 3종) | `efct_skill_121/122/123` | `game_skill_121/122/123` | 강력폭발/불꽃/눈꽃 |

"페인트 풍선 트랩"은 PDF에서도 가칭이며 전용 에셋이 없다. **P0 제외.**

### 3.6 AI 상대

```
탐색 소요시간(초) = clamp( (7 − level × 0.03) × (1 + U(−0.15, +0.15)), 1.0, 7.0 )
```

- 공격력·방어력·스킬 풀은 플레이어 캐릭터와 동일하게 적용하고, 스킬은 랜덤 발동.
- **트리거**: 매칭 큐 진입 후 5초 내 상대가 없으면 AI 대전으로 전환.
- **난입**: AI로 전환된 일반 매칭 판에 실제 대기자가 들어오면 진행 중인 판을 중단하고
  매칭방으로 이동시킨다. (별도 AI 연습 모드는 P1 — 난입 없음)
- **실행 위치**: 서버. 클라 AI는 치팅 벡터이자 난입 처리의 걸림돌이다.

### 3.7 레벨 계급 (시력 컨셉)

지렁이 → 두더지 → 박쥐 → 곤충 → 개 → 토끼 → 사람 → 고양이 → 매 → 독수리 → 타조 (11계급).

레벨 1–100을 11계급에 매핑한다. P0는 계급 **표시만** 구현하고, 레벨 곡선·능력치 테이블은
`legacy/server/src/util/balance.js`의 `LEVEL_SCORE` / `LEVEL_ABILITY`(101행)를 그대로 이식한다.

### 3.8 동기화 모델 — 대칭

두 플레이어는 **같은 퍼즐과 같은 5개 노출**을 받는다. 원작의 비대칭(각자 다른 이미지) 구조는
채택하지 않는다.

근거: PDF Part 1은 비대칭을 **"동기화 기술 한계를 보완하기 위해"** 도입했다고 직접 밝힌다.
즉 디자인 의도가 아니라 2012년 네트워크 제약의 산물이며, 서버 권위 + WebSocket 구조에서는
그 제약 자체가 사라진다. 비대칭을 떠받치던 두 번째 축인 "유저별 광고 이미지 노출"도
Part 2가 강제 광고를 제거하면서 명분을 잃는다.

대칭이 가져오는 것:

- 순수 실력 대결이 되어 P2의 ELO/MMR 시즌 랭크전이 성립한다. 비대칭에서는 "내 퍼즐이 더
  어려웠다"는 공정성 문제가 구조적으로 남는다.
- 서버가 단일 매치 상태만 들면 되므로 판정·리플레이·관전 구현이 모두 단순해진다.

대칭이 만드는 위험과 대응: 같은 퍼즐을 반복해서 만나면 암기가 가능해진다. 5-of-7 랜덤
노출로 같은 퍼즐도 매번 다르게 보이게 해 완화하고, 근본 해결은 P3의 AI 생성 콘텐츠에 맡긴다.

**퍼즐 배정은 `PuzzleAssigner` 한 곳으로 격리한다.** 캐주얼=비대칭 / 랭크=대칭으로 나누는
결정이 나오면 이 클래스 하나를 교체하는 작업이 된다.

## 4. 레포 구조

```
findit-rebuild/
├─ legacy/                    ← git mv. 이력 보존, 읽기 전용 참조
│   ├─ android_project/         2012 원작 디컴파일 — 좌표·공식 진실 출처
│   ├─ decoded_apk/             원본 에셋 진실 출처 (PNG 670 + OGG 11)
│   ├─ jadx_output/
│   ├─ client_flutter/          v1 재구축본 — 공식 참조용
│   ├─ server/                  v1 Node 서버 — balance.js 이식원
│   └─ artifacts/               *.apk, *.zip
├─ app/                       ← 신규 Flutter + Flame
├─ server/                    ← 신규 Node + TypeScript
├─ packages/protocol/         ← 클라·서버 공유 메시지 스키마
├─ content/                   ← 파이프라인 산출물 (퍼즐 JSON + 이미지)
├─ tools/                     ← 추출 스크립트
└─ docs/                      ← 기존 유지 + superpowers/specs/
```

`legacy/`는 삭제가 아닌 **격리**다. `tools/`가 거기서 읽어 `content/`와 `app/assets/`를
생성하므로 빌드 의존성으로 살아 있다.

## 5. 에셋 파이프라인

원작 에셋 재사용은 수작업 복사가 아니라 **재실행 가능한 추출 스크립트**로 한다.
좌표 284개를 손으로 옮기면 검증이 불가능하다.

| 스크립트 | 입력 | 출력 |
|---|---|---|
| `tools/extract-puzzles.ts` | `legacy/android_project/…/Objects.java` | `content/puzzles/a00NN.json` — 30세트 × rect 7개 |
| `tools/extract-images.sh` | `legacy/decoded_apk/res/drawable-hdpi-v4` | `content/images/a00NN/{base,patch_01..07}.webp` |
| `tools/extract-ui.sh` | 동일 | `app/assets/legacy/` — UI·캐릭터·아이템·이펙트 189장 |
| `tools/extract-audio.sh` | `legacy/decoded_apk/res/raw` | `app/assets/audio/*.ogg` — 11개 |

### 5.1 좌표 추출 세부

`Objects.java::createBaseFindImages()` (L434–1016)가 30개 `FindImage`와 284개 `FindRect`를
하드코딩하고 있다. jadx가 상수를 심볼로 치환해 놓았으므로 역치환이 필요하다.

```
Defines.DIALOG_STATE.DLG_DOTORI_AUTH_DIALOG → 130
Defines.DIALOG_STATE.DLG_AUTO_PURCHASE      → 110
(그 외 DIALOG_STATE.* 는 legacy/…/feelingk/iap/util/Defines.java 에서 전량 로드)
```

출력 스키마:

```json
{
  "id": "a0001",
  "width": 640,
  "height": 720,
  "rects": [
    { "index": 0, "x": 187, "y": 340, "w": 130, "h": 130, "patch": "patch_01.webp" }
  ]
}
```

**검증**: 추출된 rect 수가 소스의 `mFindRectTotalnum`과 일치하는지, 모든 rect가 이미지 경계
안에 있는지 스크립트가 단언한다. 불일치 시 빌드 실패.

### 5.2 알려진 제약 — 레거시 에셋 해상도

레거시 비트맵은 hdpi 시대 해상도다 (`main_btn_1` 450×144, `bg` 1280×800, 캐릭터 360×500,
아이템 아이콘 112×112). 3x 단말에서 전체폭 버튼은 약 1200px가 필요하므로 대형 버튼을
그대로 늘리면 2.7배 업스케일로 흐려진다.

**대응**: §7의 하이브리드 아트 방향이 이 제약에 대한 답이다. 대형 UI 크롬은 코드 렌더로
대체하고, 레거시 비트맵은 실사용 크기가 작은 곳(아이템 아이콘, 캐릭터, 이펙트, 퍼즐 이미지,
결과 화면 엠블럼)에만 쓴다.

## 6. 서버 설계

### 6.1 모듈 경계

```
server/src/
├─ identity/    계정 · 게스트 · 세션 토큰
├─ content/     퍼즐 매니페스트 · 배포 · 난이도
├─ match/       매칭 큐 · 대기실 · 방
├─ battle/      권위 배틀 엔진               ★
├─ economy/     코인 · 경험치 · 인벤토리
├─ ai/          AI 상대 시뮬레이터
├─ realtime/    WS 게이트웨이 · 프로토콜
└─ platform/    pg · redis · config · log
```

모듈 간은 **공개 인터페이스 경유만** 허용하고 교차 import를 ESLint 경계 규칙으로 차단한다.
트래픽이 생기면 이 선에서 그대로 떼어내 서비스화한다 — PDF의 마이크로서비스 목표로 가는
경로를 지금 비용 없이 확보하는 장치다.

각 모듈은 "무엇을 하는가 / 어떻게 쓰는가 / 무엇에 의존하는가"에 답할 수 있어야 한다.
`battle`은 `content`에서 퍼즐을, `economy`에서 능력치를 받지만 둘의 내부는 모른다.

### 6.2 배틀 엔진 — 틱이 아닌 이벤트 + 권위 시계

상태기계: `WAITING → COUNTDOWN(3s) → PLAYING(40s) → ENDED`

서버는 매치당 `startedAt`(monotonic)만 보유하고, **입력이 올 때마다** `elapsed`를 재계산해
검증한다. 40초 동안 주기 틱을 쏘지 않으므로 방당 비용이 거의 0이고, 클라 타이머 조작은
판정에 아무 영향을 주지 못한다.

```
TAP {x, y}
  ├─ elapsed 범위 검증 → 범위 밖이면 무시
  ├─ 입력 잠금 중이면 무시
  ├─ 히트 → REVEAL {index, rect, patchUrl}  양쪽 브로드캐스트, 콤보++
  └─ 미스 → LOCK {2000ms}  본인에게만, 콤보 리셋

SKILL {skillId}
  └─ §3.3 공식 계산 → BLIND {durationMs, effectId}  상대에게

종료: 5개 선취 | 40초 만료 | 이탈
```

**핵심 설계 결정**: 엔진은 **순수 함수 + 주입된 시계**로 작성한다.
`reduce(state, event, now) → (state', outbound[])`. 이 하나가 이 설계의 테스트 가능성을
좌우한다 — 40초 매치를 밀리초 안에 결정론적으로 검증할 수 있다.

### 6.3 치팅 방어 (PDF Part 2 명시 요구)

| 벡터 | 방어 |
|---|---|
| 좌표 조작 | 정답 좌표는 서버만 보유. 클라는 `REVEAL` 수신 전까지 위치를 모름 |
| 패치 이미지 diff | 패치 이미지는 히트 시점에 URL로 전달. 사전 프리페치 불가 |
| 타이머 해킹 | 권위 시계. 클라 타임스탬프는 판정에 쓰지 않음 |
| 격자 스캔 봇 | 미스 2초 잠금. 130px 격자 전수 스캔은 30탭 × 2초 = 60초 > 게임시간 40초 |
| 리플레이/중복 전송 | 메시지 봉투의 `seq` 단조 증가 검사 |

### 6.4 콘텐츠 배포

퍼즐 이미지·좌표는 앱 번들이 아니라 **서버 매니페스트 + 로컬 캐시**로 배포한다.
PDF의 패치 다운로드 팝업 요구사항이자, P3 AI 콘텐츠 엔진이 들어올 자리다.

```
GET /content/manifest        → { version, puzzles: [{ id, hash, sizeBytes, difficulty }] }
GET /content/images/:id/base → 이미지 바이너리 (CDN 대체 가능)
```

**좌표는 어떤 엔드포인트로도 클라에 내려가지 않는다.** 클라가 받는 것은 base 이미지뿐이다.

### 6.5 데이터 모델 (P0 최소)

PostgreSQL: `account`, `guest_session`, `player_profile`(level/exp/coin), `inventory_item`,
`match_history`, `content_version`.

Redis: `queue:casual`(매칭 큐), `session:{token}`, `match:{id}`(진행 중 상태, TTL 5분).

진행 중 매치를 Redis에 두는 이유는 서버 인스턴스가 늘어날 때 방 소유권을 옮길 수 있게
하기 위함이다. P0는 단일 인스턴스지만 구조는 미리 맞춘다.

## 7. 클라이언트 설계

### 7.1 구조

```
app/lib/

│   └─ result/     결과 화면                    [레거시]
├─ ui/
│   ├─ md3/      토큰 · 다크모드 · 타이포
```

상태관리는 Riverpod. Flame 게임 루프와 앱 상태를 분리해 배틀 씬이 외부 상태를 직접
읽지 않도록 한다.

### 7.2 하이브리드 아트 방향

`ui/md3`와 `ui/legacy`를 **물리적으로 분리**하는 것이 이 결정의 집행 장치다. 두 디자인
언어가 한 파일에서 섞이기 시작하면 결국 둘 다 아닌 것이 된다.

- **배틀 · 결과 화면**: 레거시 룩 — 블랙 바탕 + 포인트 컬러, 원작 이펙트/승패 엠블럼/
  카운트다운 비트맵. 이 화면들에서 에셋은 작게 쓰여 §5.2의 해상도 문제가 없다.
- **로그인 · 로비 · 대기실**: Material 3 토큰 렌더 + 다크모드 기본. 버튼·패널·배경은 코드로
  그리고, 그 위에 아이템/캐릭터 비트맵만 얹는다.

### 7.3 햅틱 (PDF 명시 요구)

정답 터치 · 오답 터치(200ms, 원작 수치) · 스킬 피격 시 햅틱 피드백.

## 8. 프로토콜

WebSocket + JSON. 메시지 봉투:

```json
{ "t": "TAP", "seq": 17, "d": { "x": 231, "y": 402 } }
```

`packages/protocol/`에 스키마를 **한 번만** 정의하고 Dart·TypeScript 타입을 생성한다.
클라와 서버가 같은 메시지를 두 번 정의하면 반드시 어긋난다.

| 방향 | 메시지 |
|---|---|
| C→S | `AUTH` `QUEUE_JOIN` `QUEUE_LEAVE` `READY` `TAP` `SKILL` `LEAVE` |
| S→C | `QUEUED` `MATCH_FOUND` `COUNTDOWN` `START` `REVEAL` `LOCK` `BLIND` `OPPONENT_PROGRESS` `END` `ERROR` |

바이너리·protobuf 전환은 대역폭이 문제가 된 뒤 검토한다. P0에서는 JSON의 디버깅 용이성이
더 가치 있다.

## 9. 테스트 전략

TDD로 진행한다. 테스트를 먼저 쓰고 실패를 확인한 뒤 구현한다.

| 계층 | 도구 | 대상 |
|---|---|---|
| 배틀 엔진 | vitest | 순수 리듀서 — 상태 전이, 히트/미스, 종료 조건, 잠금 |
| 공식 | vitest 테이블 테스트 | §3의 모든 표를 fixture로 고정 (스킬 지속시간, AI 시간, 점수, 콤보) |
| 좌표 추출 | vitest | 30세트 × rect 수가 소스와 일치, 경계 검사 |
| 통합 | vitest + ws | WS 클라이언트 2개로 풀 매치 시나리오 |
| 클라 로직 | flutter_test | 상태 전이, 프로토콜 파싱 |
| 클라 UI | flutter_test golden | 레거시 룩 화면 회귀 |

**§3의 수치표를 fixture로 박는 것**이 회귀 방지의 핵심이다. 밸런스 값은 시간이 지나면
누군가 "대충 이 정도겠지"로 바꾸게 되는데, 테이블 테스트가 그것을 즉시 붙잡는다.

## 10. P0 완료 정의

1. 게스트 또는 계정으로 로그인 → 로비 진입
2. 매칭 큐 진입 → 5초 내 상대 없으면 AI 대전 전환
3. 3초 카운트다운 → 40초 배틀, 5-of-7, **모든 판정 서버**
4. 손도장 계열 스킬 + 아이템 3종(`pen_01`, `ring_01`, `posion_01`) 동작
5. 결과 화면 — 승/패, 코인·경험치 정산이 DB에 반영
6. 퍼즐 30세트가 서버 매니페스트로 배포되고 클라가 캐싱
7. iOS·Android 빌드 통과 + `docker compose up` 기동 + 전체 테스트 그린
